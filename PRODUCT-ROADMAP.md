## Product direction

Portcn is a read-only local runtime inspection CLI. Linux provides the full current command set; the development branch adds macOS listener discovery for `list`, `inspect`, and `diagnose`. Windows remains unsupported. Portcn discovers visible TCP/UDP listeners, inspects a port, diagnoses visible owners and visibility limits, and provides interactive terminal views. It does not terminate processes. Product work should first make port-conflict diagnosis dependable, then build project context and safe read-only ownership explanations before expanding into integrations.

Portcn overlaps with `ss`, `lsof`, `netstat`, and small port-killer utilities in inspecting local sockets. Its intended distinction is beginner-readable explanations, one coherent view of visible owners and namespace limits, project context, and stable agent-facing read-only contracts. These are product goals, not claims that every capability is already implemented. Portcn does not replace those system tools or guarantee visibility beyond the current user and namespaces.

## Standalone distribution evaluation (#143)

**Recommendation:** Keep npm as Portcn's primary user-facing distribution channel; do not add standalone executables yet. The release workflow also publishes a scoped GitHub Packages package, which changes the registry route but still requires Node.js. The published `v0.5.0` package requires Node.js 24 or newer and supports Linux. The development package lowers the Node.js floor to 22 after #142; #140's macOS discovery has merged to `dev`, but neither change is in the published package yet. This evaluation does not establish Windows or macOS release support.

| OS package manager                           | A package could install Portcn and declare Node as a dependency; it does not by itself remove the Node prerequisite.                                                           | No standalone-runtime benefit unless the runtime is bundled.                                                                                                                                                                            | Each package format adds repository, metadata, signing, update, and support work. The recommendation is to keep the existing npm release pipeline and avoid a binary prototype in this issue. Revisit when user feedback shows the Node prerequisite blocks adoption or when install telemetry provides a concrete target. If that happens, prototype a Linux x64 SEA first to measure executable size, startup, clean-machine installation, and support burden before adding more operating systems or architectures. Keep macOS and Windows distribution decisions separate from their listener-discovery work.
