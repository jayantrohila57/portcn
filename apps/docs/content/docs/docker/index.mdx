Docker support includes an optional packaging workflow and a development-branch read-only container inventory command. Git hooks and GitHub Actions do not require Docker. Container runs see only sockets exposed in the container's network namespace; running Portcn in its packaged image does not add host discovery or service management.

## Inspect local containers

The development command ``portcn docker`` lists running and stopped containers from the Docker CLI's selected daemon context. It reports Compose project/service labels, configured health, network addresses, exposed ports, published host bindings, and any matching host listeners visible in Portcn's current namespace. A stopped container's saved port configuration is labeled configured rather than active.

```sh
portcn docker
portcn docker --json
```

This is a read-only Docker CLI query. Missing Docker, denied daemon access, and an unavailable daemon are reported separately. Port mappings describe Docker configuration; matching listeners are observations and do not prove reachability. Listener observations come from Portcn's current network namespace and may not describe a remote Docker daemon host. IPv6 routed-mode mappings without a host port are reported as direct routes. Host-network containers share the host network stack and are not attributed from exposed-port metadata alone.

## Classify potential exposure

Use ``portcn exposure`` to combine visible host listeners with Docker mapping metadata and classify loopback, interface-specific, wildcard, direct-routed, and container-only scopes:

```sh
portcn exposure
portcn exposure --json
```

The command does not inspect firewalls or test remote reachability. Wildcard scope is not a claim that a service is publicly reachable. Docker's [port publishing reference](https://docs.docker.com/engine/network/port-publishing/) notes that localhost-published ports may be reachable by same-layer-2 peers with Engine versions before 28.0.0; Portcn does not inspect that version.

## Build the CLI image

From the repository root:

```sh
docker compose -f infra/docker/compose.yaml --profile cli build cli
docker compose -f infra/docker/compose.yaml --profile cli run --rm cli --help
```

The image uses Node.js 24, builds the CLI and core packages, packs the CLI package, and installs that package into a small runtime image.

## Run repository checks

```sh
docker compose -f infra/docker/compose.yaml --profile test run --build --rm test
```

The optional test image installs the frozen workspace lockfile and runs branch policy, lint, format, types, tests, build, package, workspace boundary, release metadata, and documentation checks. To validate commit headers as well, set `PR_BASE_SHA` and `PR_HEAD_SHA` in the Compose environment. GitHub Actions runs the workspace checks directly on its runner and does not use Docker Compose.

<Callout title="Docker requirements" type="info">
Install Docker Engine with the Compose plugin. The test profile mounts `.git` read-only so branch policy and optional commit checks can inspect repository history. It does not mount the Docker socket into the container.
</Callout>

## Troubleshooting

<Accordions type="single">
  <Accordion title="The CLI image build cannot find a package">
    Run Compose from the repository root and keep the build context at the repository root. The configured Dockerfile relies on workspace manifests and the frozen lockfile.
  </Accordion>
  <Accordion title="The test profile rejects my branch">
    Branch policy is designed for pull requests targeting `dev` or approved integration routes. Local-only branches may not meet PR policy. Use the local checks that apply to your task, and let CI evaluate the actual PR route.
  </Accordion>
</Accordions>
