Docker support includes an optional packaging workflow and a released read-only container inventory command. Git hooks and GitHub Actions do not require Docker. Container runs see only sockets exposed in the container's network namespace; running Portcn in its packaged image does not add host discovery or service management.

## Inspect local containers

The ``portcn docker`` command lists running and stopped containers from the Docker CLI's selected daemon context. It reports Compose project/service labels, configured health, network addresses, exposed ports, published host bindings, and any matching host listeners visible in Portcn's current namespace. A stopped container's saved port configuration is labeled configured rather than active.

```sh
portcn docker
portcn docker --json
```

This is a read-only Docker CLI query. Missing Docker, denied daemon access, and an unavailable daemon are reported separately. Port mappings describe Docker configuration; matching listeners are observations and do not prove reachability. Listener observations come from Portcn's current network namespace and may not describe a remote Docker daemon host. IPv6 routed-mode mappings without a host port are reported as direct routes. Host-network containers share the host network stack and are not attributed from exposed-port metadata alone.

## Inspect Podman containers

Use ``portcn podman`` to inspect running and stopped containers visible through the current Podman user and configured connection. Podman commands run as the invoking user, so the same command can discover rootless containers owned by that user or rootful containers when the caller already has access. Portcn never elevates privileges. It reports Podman Compose labels, health, network mode and addresses, exposed ports, published mappings, and matching local listeners.

```sh
portcn podman
portcn podman --json
```

Podman inventory uses only read-only ``container ls`` and ``container inspect`` operations. It does not start, stop, exec into, or reconfigure containers. A stopped container's port mapping remains configured, not active. For active published bindings on Linux, Portcn may report a ``rootlessForwarder`` attribution when a visible listener PID resolves to the ``rootlessport`` executable, its structured host/container mapping matches the binding and container network address, and its PID start time remains stable. Attribution is marked ``ambiguous`` when candidates conflict and ``unknown`` when evidence is missing or inaccessible. It is advisory process evidence, not proof of reachability. Listener matches come from Portcn's current network namespace and do not establish identity of a remote connection. Docker and Podman records remain separate command outputs; safe identity reconciliation is provided in the shared discovery layer.

## Inspect local Nginx configuration

Use ``portcn nginx`` to read local Nginx server blocks and visible Nginx processes on Linux. The command reads the default ``/etc/nginx/nginx.conf`` and local included files; pass ``--config <path>`` to select another entry file. It reports only server names, listen addresses and ports, source file paths, and whether a matching local listener was observed.

```sh
portcn nginx
portcn nginx --config ./nginx.conf --json
```

Nginx configuration remains configured evidence. ``observed`` and ``not-observed`` describe a point-in-time comparison with listeners in Portcn's current network namespace, not request routing or virtual-host reachability. Unreadable files and missing include matches produce partial results. Portcn does not invoke Nginx, reload it, elevate privileges, or return unrelated directive values.

## Classify potential exposure

Use ``portcn exposure`` to combine visible host listeners with Docker mapping metadata and classify loopback, interface-specific, wildcard, direct-routed, and container-only scopes:

```sh
portcn exposure
portcn exposure --json
```

The command does not inspect firewalls or test remote reachability. Wildcard scope is not a claim that a service is publicly reachable. Docker's [port publishing reference](https://docs.docker.com/engine/network/port-publishing/) notes that localhost-published ports may be reachable by same-layer-2 peers with Engine versions before 28.0.0; Portcn does not inspect that version.

## Build the CLI image

From the repository root:

```sh
docker compose -f infra/docker/compose.yaml --profile cli build cli
docker compose -f infra/docker/compose.yaml --profile cli run --rm cli --help
```

The image uses Node.js 24, builds the CLI and core packages, packs the CLI package, and installs that package into a small runtime image with ``iproute2`` for Linux listener discovery. It sees only sockets in its isolated network namespace; it does not gain host listener or process visibility.

## Run repository checks

```sh
docker compose -f infra/docker/compose.yaml --profile test run --build --rm test
```

The optional test image installs the frozen workspace lockfile and runs branch policy, lint, format, types, tests, build, package, workspace boundary, release metadata, and documentation checks. It marks only ``/workspace`` as a Git safe directory so the read-only mounted ``.git`` metadata can be checked when host and container ownership differ. To validate commit headers as well, set `PR_BASE_SHA` and `PR_HEAD_SHA` in the Compose environment. GitHub Actions runs the workspace checks directly on its runner and does not use Docker Compose.

<Callout title="Docker requirements" type="info">
Install Docker Engine with the Compose plugin. The test profile mounts `.git` read-only so branch policy and optional commit checks can inspect repository history. It does not mount the Docker socket into the container.
</Callout>

## Troubleshooting

<Accordions type="single">
  <Accordion title="The CLI image build cannot find a package">
    Run Compose from the repository root and keep the build context at the repository root. The configured Dockerfile relies on workspace manifests and the frozen lockfile.
  </Accordion>
  <Accordion title="The test profile rejects my branch">
    Branch policy is designed for pull requests targeting `dev` or approved integration routes. Local-only branches may not meet PR policy. Use the local checks that apply to your task, and let CI evaluate the actual PR route.
  </Accordion>
</Accordions>
