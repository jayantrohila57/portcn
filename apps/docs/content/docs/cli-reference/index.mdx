The published ``v0.7.0`` CLI package requires Node.js 22 or newer; the source workspace and build require Node.js 24 or newer. Linux is the primary supported platform. The package also includes limited macOS ``list``, ``inspect``, and ``diagnose`` support through ``lsof``. On macOS, process command lines, user IDs, project context, and agent markers are unavailable. Windows listener discovery is not implemented. The macOS CI integration verifies real listener discovery; other command families are supported on Linux unless stated otherwise.

| Platform | Verified CLI support | Requirements and limits |
| --- | --- | --- |
| Linux | All documented command families, including the dashboard and MCP server | `ss` from `iproute2`; Docker and Podman commands require the respective CLI and access to the selected runtime/context. Visibility remains namespace- and permission-limited. |
| macOS | `list`, `inspect`, and `diagnose` listener discovery | System `lsof`; visible PID/process names only. The live macOS CI check covers listener discovery. Linux `/proc`, project, and agent-marker details are unavailable. |
| Windows | Help and version output | Listener/service discovery is unsupported. |

Registered top-level commands include `list`, `inspect`, `diagnose`, `wait`, `check`, `suggest`, `assess`, `verify`, `config`, `endpoint`, `open`, `readiness`, `connection`, `docker`, `podman`, `nginx`, `systemd`, `exposure`, `discover`, and `mcp`. Configuration subcommands include `add`, `edit`, `remove`, `group`, and `recover`.

## ``portcn config``

Save service identities using their protocol, bind address, and port. A service can have a favorite, alias, note, and memberships in multiple groups. The identity includes protocol and the exact bind address, so TCP/UDP and wildcard/specific binds remain distinct. Use `add`, `edit`, and `remove` for saved services, and `group` to manage group records.

```sh
portcn config add tcp 127.0.0.1 3000 --favorite --alias web --group local --group projects --url http://127.0.0.1:3000/
portcn config group add projects
portcn config edit tcp://127.0.0.1:3000 --favorite false --note "development server" --url https://localhost:3000/
portcn config edit tcp://127.0.0.1:3000 --clear-url
portcn config list
portcn config list --json
portcn config remove tcp://127.0.0.1:3000
portcn config group remove local
portcn config recover
```

The configuration is stored at ``$XDG_CONFIG_HOME/portcn/config.json`` or ``~/.config/portcn/config.json`` when ``XDG_CONFIG_HOME`` is unset. Portcn restricts the directory to owner access and the file to mode ``0600``. Writes use a same-directory temporary file and retain the preceding valid version as ``config.json.bak``. Config versions 0 and 1 migrate to version 2; old services receive no URL override. URL overrides require HTTP(S), an explicit matching port, no URL credentials, and a localhost, loopback, or service-bind host. A host address is offered only when it belongs to a local interface. If the primary file is invalid, the CLI uses a valid backup with a warning; ``recover`` explicitly restores that backup. Invalid config without a valid backup is reported and left untouched. Saved status is ``online`` or ``offline`` only when listener discovery succeeds; it is ``unknown`` when discovery is unavailable. Process metadata and discovery results are never persisted.

## ``portcn endpoint`` and ``portcn open``

Endpoint candidates come only from currently observed local listeners and use saved service details when available. Wildcard IPv4 and IPv6 binds map to loopback URLs; a TCP candidate without a user override is marked ``unverified`` because a port does not establish HTTP(S). UDP services and services without an eligible local address are marked ``non-web``. ``endpoint list`` never probes a service; JSON output includes the candidate state and verification status.

```sh
portcn endpoint list
portcn endpoint list --json
portcn endpoint check tcp://127.0.0.1:3000
portcn endpoint check tcp://127.0.0.1:3000 --timeout 2500 --json
portcn open tcp://127.0.0.1:3000
```

``endpoint check`` sends one HTTP ``HEAD`` request to the selected saved service, with a default 1500 ms timeout capped at 5000 ms. It reports an HTTP response, timeout, TLS validation failure, or unreachable endpoint; it does not claim application readiness. Redirects are not followed, and HTTPS uses Node's default certificate validation. ``open`` is an explicit action and invokes ``xdg-open`` without a shell, with the validated local URL as one argument. Terminal output uses OSC 8 hyperlinks only when stdout is a TTY; piped output contains plain URLs. JSON output uses schema version 1. The request and browser action do not visit remote hosts.

## ``portcn readiness`` (`readiness`)

Readiness is an explicit, bounded check of one saved or currently observed local service. ``readiness list`` reports listener snapshots as ``listening`` and saved services without a matching listener as ``stopped``; neither state is inferred from a prior probe. ``readiness check`` uses a TCP connection when no saved URL is configured and reports ``reachable`` only, which does not establish application readiness. With a saved local HTTP(S) URL, it sends bounded ``HEAD`` requests without following redirects: 2xx is ``ready``, a received non-2xx response after retries is ``unhealthy``, and no conclusive response is ``unknown``. UDP entries remain ``listening`` because these probes do not apply.

```sh
portcn readiness list
portcn readiness list --json
portcn readiness check tcp://127.0.0.1:3000
portcn readiness check tcp://127.0.0.1:3000 --timeout 1500 --retries 2 --interval 250 --json
```

The timeout applies per attempt (100–5000 ms), retries are capped at five (default two), and the interval is capped at 2000 ms (default 250). Ctrl-C or SIGTERM cancels the in-flight probe or wait. Results use JSON schema version 1 with attempt count, endpoint mode, observation time, HTTP status when received, and a human-readable detail. A missing current listener is reported as ``stopped`` without sending a probe. All probes target the validated local bind or saved local URL; Portcn does not issue arbitrary shell checks, restart services, or make external requests.

## ``portcn connection`` (`connection`)

Run staged diagnostics for one saved or currently observed service from the current host and network namespace. The command resolves the local bind target, reports IPv4/IPv6 addresses and bind scope, attempts TCP connections with a bounded per-address timeout, checks an explicitly saved HTTP(S) URL when present, and adds matching Docker host-port mapping metadata when the Docker CLI is available. A successful TCP connection proves reachability only from Portcn's current namespace. Docker mapping records are configuration evidence and do not prove container reachability; a remote Docker context may describe a different host.

```sh
portcn connection check tcp://127.0.0.1:3000
portcn connection check tcp://127.0.0.1:3000 --timeout 2500 --json
```

The timeout defaults to 1500 ms and is capped at 5000 ms per TCP address and HTTP request. JSON schema version 1 contains observation time, hostname and network namespace, per-stage statuses and evidence, per-address connection outcomes, Docker mappings, and limitations. Refusal, timeout, resolution failure, HTTP redirect, non-success response, and TLS validation failure remain distinct. Redirects are not followed and certificate validation is not disabled. UDP services include bind and Docker evidence but skip TCP and HTTP probes. The command does not scan external hosts, inspect firewall rules, execute commands in containers, or change system state.

## ``portcn docker``

Read a snapshot of all containers in the Docker CLI's selected daemon context, including stopped containers. Portcn lists container IDs and inspects them without changing container state. The output includes state, configured health, Compose project/service labels, network addresses, exposed ports, and published host bindings. Stopped containers can retain mapping configuration; Portcn labels those entries as configured and does not treat them as active host bindings.

```sh
portcn docker
portcn docker --json
```

Ports marked ``exposed`` are container metadata and are not necessarily published or listening. Published bindings retain every host address and port, including separate IPv4 and IPv6 mappings. IPv6 routed-mode entries with no host port are marked ``direct``. Portcn compares published host bindings with visible local TCP/UDP listeners by protocol, port, and bind address; this is a point-in-time observation, not proof of reachability or ownership by a Docker proxy process. When the Docker context is remote, listener observations still come from Portcn's current network namespace and may not describe the daemon host. Host-network containers share the host network stack, so Portcn does not attribute listeners to them from declared exposed ports alone. Docker CLI absence, daemon unavailability, and permission denial have distinct statuses and return code 1; ``--json`` emits a version 1 result with a stable error code.

## ``portcn podman``

Inspect containers visible through the current Podman user and configured connection. Rootless and rootful inventories follow the caller's existing access; Portcn does not elevate privileges. The command reports Compose labels, health, network mode and addresses, exposed ports, published mappings, and visible host listeners.

```sh
portcn podman
portcn podman --json
```

Only read-only ``podman container ls`` and ``podman container inspect`` operations are used. Missing CLI, denied access, unavailable service/connection, and malformed inventory are distinct in schema version 1 JSON. Stopped mappings are configured, not active. On Linux, active published bindings include ``rootlessForwarder`` with ``attributed``, ``ambiguous``, or ``unknown`` status. Attribution requires a visible listener owner, the ``rootlessport`` executable, matching structured host/container mapping and network address, and a stable PID start time. Listener and process observations come from Portcn's current namespace and do not prove reachability; a remote runtime may describe another host. Docker and Podman remain separate command outputs.

## ``portcn nginx``

The `nginx` command inspects readable local Nginx configuration and visible Nginx executable paths on Linux. The default configuration entry is ``/etc/nginx/nginx.conf``; ``--config <path>`` selects another entry. Schema version 1 JSON includes process PIDs, source paths, server names, configured TCP listeners and their observed/not-observed/unknown state, availability, and limitations. Only server names and listen directives are surfaced from configuration.

```sh
portcn nginx
portcn nginx --config ./nginx.conf --json
```

Includes are followed through local readable files with a 256-file bound. Missing or unreadable files yield partial results. A configured listener does not establish active routing or reachability; matching sockets are read from Portcn's current network namespace. The command does not run or reload Nginx and does not elevate privileges.

## ``portcn systemd``

The `systemd` command reads visible user and systemd service/socket units. Schema version 1 JSON includes each manager's availability separately, unit scope and state, MainPID when present, matching listener ports for MainPID, and socket listen endpoints with point-in-time observation state. Missing `systemctl`, an unavailable user manager, and permission denial remain distinct.

```sh
portcn systemd
portcn systemd --json
```

The command is read-only. It does not elevate privileges or start, stop, restart, enable, or disable units. Socket activation configuration is kept distinct from a live service process; only the unit's MainPID is used for process/listener correlation.

## ``portcn exposure``

Classify each visible host listener and Docker port record by address family and bind scope. Loopback, interface-specific, wildcard, direct-routed, and container-only records remain distinct. A wildcard address means the socket or mapping uses all addresses in that family; it does not establish internet reachability. Portcn does not inspect firewalls, routers, external routes, or public reachability.

```sh
portcn exposure
portcn exposure --json
```

The version 1 JSON report includes an observation timestamp, listener and Docker availability, findings, and limitations. Docker findings use the currently selected Docker CLI context; listener observations come from Portcn's current network namespace and may refer to a different host for remote contexts. Docker daemon permission or availability failures do not hide successfully discovered host listeners. The command returns code 1 only when both listener discovery and Docker inventory are unavailable.

Docker documents a same-layer-2 reachability caveat for localhost-published ports with Engine versions earlier than 28.0.0. Portcn does not inspect the daemon version; see Docker's [port publishing and mapping reference](https://docs.docker.com/engine/network/port-publishing/).

```sh
node apps/cli/dist/index.js --help
node apps/cli/dist/index.js list
```

For an interactive view, use ``--interactive`` or run ``portcn`` without arguments. The listener tabs show bind address, owner PID/process, and best-effort project evidence when visible. On Linux, press ``5`` for a service view combining native listeners, Docker, Podman, Nginx configuration, and systemd service/socket units. Service details retain source, configured/observed state, endpoint, owner/project scope, and evidence; provider failures remain visible as status records. Press ``1`` for all listeners, ``2`` for TCP, ``3`` for UDP, ``4`` for listeners with visible processes, ``Tab`` for the next tab, ``n`` or Space for the next page, ``p`` for the previous page, and ``q`` or ``Esc`` to quit. Arrow keys or ``j``/``k`` move selection; details follow the selected row. Provider snapshots refresh from the command palette and five-second auto-refresh. Interactive mode requires a terminal; piped output remains the normal listener table.

```sh
node apps/cli/dist/index.js list --interactive
node apps/cli/dist/index.js list --json
node apps/cli/dist/index.js inspect 3000 --json
node apps/cli/dist/index.js diagnose 3000 --json
```

The `--json` forms emit complete results without pagination, colors, or screen-control sequences. `list --json` and `inspect --json` retain their existing top-level array format for compatibility. `diagnose --json` emits its versioned diagnosis object.

All three commands also accept ``--json-version 1`` for a stable, deterministic envelope. This additive option preserves the successful legacy `--json` shapes.

## ``portcn list``

Lists listening TCP and UDP sockets on Linux or macOS. Linux requires ``ss`` (provided by ``iproute2`` on Ubuntu) and runs ``ss --no-header --listening --tcp --udp --numeric --processes``. macOS runs two ``lsof`` queries: ``lsof -nP -iTCP -sTCP:LISTEN -F0pcPn`` and ``lsof -nP -iUDP -F0pcPn``. They run without a shell and perform read-only discovery. macOS UDP entries have no socket state from ``lsof`` and are represented as ``UNCONN``; connected UDP endpoints are excluded. Neither path changes ports, processes, or services.

```sh
node apps/cli/dist/index.js list
```

Output is rendered as an ASCII table with colored headers and protocol/state values in a capable interactive terminal. Color is omitted when output is piped, ``NO_COLOR`` is set to a non-empty value, or ``TERM=dumb``. Columns are ``PROTO`` (TCP/UDP), ``STATE``, ``PORT`` (numeric), ``LOCAL ADDRESS`` (bind address), ``PID`` and ``PROCESS``. Results are sorted by ascending port number. PID and process may display `` - `` when the operating system does not expose ownership to your current user. You do not need to run with sudo just to list visible sockets.

Example with sample data from tests:

```text
PROTO  STATE   PORT  LOCAL ADDRESS  PID  PROCESS
TCP    LISTEN  22    [::]           12   sshd
TCP    LISTEN  3000  127.0.0.1      321  node
UDP    UNCONN  5353  0.0.0.0        -    -
```

If no listening sockets are found, Portcn prints ``No listening TCP or UDP ports found.``

## ``portcn inspect <port>``

The `inspect` subcommand inspects all visible TCP and UDP listeners for one port using the same read-only platform discovery as ``list``. It prints a bordered ASCII table with protocol, socket state, local address, PID, process name, and best-effort command details. Linux reads command details from ``/proc``; macOS reports them as unavailable. IPv4, IPv6, and multiple listeners are retained. A missing listener is informational and returns status 0; an invalid port returns status 2. Interactive terminals receive color; piped output stays plain.

```sh
node apps/cli/dist/index.js inspect 3000
```

The command never changes sockets or processes and does not require elevation. Process details may show ``unavailable`` when access is restricted or when running on macOS. Platform discovery requirements are the same as ``list``.

## ``portcn diagnose <port>``

Diagnoses every TCP or UDP listening socket visible on the requested port. It reuses the read-only platform discovery used by ``list`` and ``inspect`` and reports each bind address, IPv4/IPv6 family, socket state, and visible PID/process owners. On Linux, it adds best-effort command and user details from ``/proc``, plus project context from the process working directory and up to five parent processes. macOS uses ``lsof`` for socket owners; command lines, user IDs, project context, and agent markers are reported unavailable. Linux project evidence remains current filesystem facts and does not prove which source the running process loaded. Shared sockets with multiple visible PIDs appear once in JSON with an ``owners`` array and as one row per owner in terminal output.

Project context is evidence, not proof that a project launched or owns a service. Portcn reads only the owner and a bounded parent chain; it does not scan repositories or inspect agent conversations. Paths and executable locations are included in JSON when visible. A PID start-time check discards context if the process exits or the PID is reused during inspection. Git metadata lookup is read-only and time-limited.

Agent attribution is opt-in. Set ``PORTCN_AGENT_SESSION_ID`` to a non-secret identifier and optionally ``PORTCN_AGENT_NAME`` in a process environment to associate that process tree with an agent session. Portcn inspects the owner and bounded ancestors' ``/proc/<pid>/environ`` files to extract only those two keys; other environment values are not retained or emitted. IDs and names are limited to 80 safe characters. Attribution reports ``associated``, ``ambiguous``, or ``unknown`` and includes its evidence, observation time, and source. ``high`` confidence means the marker was directly present on the owner; ``medium`` means it was found on an ancestor; these describe where the opt-in marker was observed, not whether the claimed agent identity is authentic. A possible leftover means the owner has a marker but no inspected ancestor has the same marker. It is a hint only; Portcn cannot verify whether a session is alive, and a leftover must never be treated as permission to stop a process.

## ``portcn assess <pid>``

The command named `assess` compares visible ownership evidence for one PID with a supplied Git project and, optionally, an opt-in agent session ID. The project path must exist inside a Git repository. The command reads a stable PID/start-time identity before and after collecting project and agent evidence; if the process exits or the PID is reused, it discards that evidence. Results include the current PID namespace and a UTC observation time.

```sh
node apps/cli/dist/index.js assess 1234 --project "$PWD"
node apps/cli/dist/index.js assess 1234 --project "$PWD" --session session-7 --json
```

The JSON schema version 1 result contains ``status`` (``matching``, ``different``, ``ambiguous``, or ``unknown``), ``identity``, ``expectedProject``, ``expectedSessionId``, ``processProject``, ``agentAttribution``, matching/different evidence arrays, ``observedAt``, ``pidNamespace``, ``limitations``, and a human-readable ``message``. A session is compared only when ``--session`` is supplied. Exit status ``0`` means the assessment completed, including unknown/ambiguous/different results; ``1`` is an unexpected runtime failure; ``2`` is invalid input or an unsupported JSON schema version. The output is advisory evidence only and never authorizes signaling or stopping a process.

## ``portcn verify <endpoint>``

The command named `verify` compares a local TCP listener with the expected Git checkout. Supply `--project <path>` and an endpoint such as `127.0.0.1:3000`, `[::1]:3000`, or `https://localhost:8443/health`. Only `localhost` and IPv4/IPv6 literals are accepted; DNS is not used. An endpoint path is ignored. Verification does not connect, make an HTTP request, check TLS, or execute tests.

```sh
node apps/cli/dist/index.js verify 127.0.0.1:3000 --project "$PWD"
node apps/cli/dist/index.js verify https://localhost:8443/health --project "$PWD" --json-version 1
```

The version 1 result includes ``status`` (``matching``, ``different``, ``ambiguous``, or ``unavailable``), endpoint and expected project checkout metadata, matching listeners and owner evidence, up to five discovered endpoint suggestions, ``suggestionsComplete``, ``runtimeCode``, observation time, messages, and limitations. Suggestions are included only when a visible owner’s current project root, branch, and commit match the expected checkout. The current checkout can change after a process starts; Portcn always reports loaded runtime code as ``unverified``. Exit status ``0`` means the comparison completed, including unavailable or ambiguous results; ``1`` is a runtime discovery failure; ``2`` is invalid input or an unsupported JSON schema version.

```sh
node apps/cli/dist/index.js diagnose 3000
node apps/cli/dist/index.js diagnose 3000 --json
node apps/cli/dist/index.js list --json-version 1
node apps/cli/dist/index.js inspect 3000 --json-version 1
node apps/cli/dist/index.js diagnose 3000 --json-version 1
```

Version 1 returns ``{"schemaVersion":1,"listeners":[...]}`` for ``list``, ``{"schemaVersion":1,"port":3000,"listeners":[...]}`` for ``inspect``, and the existing versioned diagnosis object for ``diagnose``. Listener and owner order is deterministic. Invalid ports and discovery failures in JSON mode produce one JSON error object on stdout and a nonzero exit status; errors use stable codes and sanitized messages.

## ``portcn check <port>``

Checks for visible listener overlap for the requested protocol and bind address. It does not bind, reserve, or connect to the port. The default is TCP on ``127.0.0.1``; use ``--protocol udp`` or an IPv4/IPv6 literal with ``--address`` to check another case.

```sh
node apps/cli/dist/index.js check 3000
node apps/cli/dist/index.js check 3000 --protocol tcp --address 0.0.0.0 --json
node apps/cli/dist/index.js check 3000 --address ::1 --json-version 1
```

The version 1 result contains ``schemaVersion``, ``port``, ``protocol``, ``address``, ``status``, ``conflicts``, ``message``, ``namespace``, and ``limitations``. Status is ``conflict-observed``, ``no-conflict-observed``, or ``unknown``. Wildcard checks across IPv4 and IPv6 can be uncertain because dual-stack settings differ. “No conflict observed” is a snapshot, not a guarantee that a later bind will succeed.

## ``portcn suggest``

Scans a bounded range using the same read-only listener snapshot and returns candidates with no observed overlap. By default it checks TCP on ``127.0.0.1``, scans ``3000-3999``, and returns up to five suggestions. ``--range`` accepts at most 1024 ports; ``--limit`` accepts 1 through 20. Unknown candidates are omitted.

```sh
node apps/cli/dist/index.js suggest
node apps/cli/dist/index.js suggest --range 4000-4100 --from 4000 --limit 3 --json
node apps/cli/dist/index.js suggest --protocol udp --address ::1 --range 5000-5100 --json-version 1
```

The result contains ``schemaVersion``, ``protocol``, ``address``, ``range``, ``suggestions``, ``namespace``, and ``limitations``. A suggestion is not reserved and may be claimed immediately by another process.

## ``portcn `wait` <port>``

Repeatedly checks for visible listener overlap until none is observed, the timeout expires, or SIGINT/SIGTERM cancels the wait. Defaults to TCP on ``127.0.0.1``, a 250 ms interval, and a 30 second timeout. ``--interval`` accepts 50–5000 ms; ``--timeout`` accepts 1–300000 ms. A status is emitted when it changes; ``unknown`` never counts as available. The command is read-only and cannot reserve the port.

```sh
node apps/cli/dist/index.js wait 3000
node apps/cli/dist/index.js wait 3000 --interval 500 --timeout 60000 --json
node apps/cli/dist/index.js wait 3000 --protocol udp --address ::1 --json-version 1
```

JSON mode writes version 1 JSON Lines: ``state-change`` events followed by an ``available`` result, or a final ``timeout``, ``cancelled``, or ``error`` event. Timeout uses ``WATCH_TIMEOUT``; cancellation uses ``WATCH_CANCELLED``. Timeout returns status 1, cancellation returns 130, invalid input returns 2, and observed availability returns 0. “No conflict observed” is only a point-in-time result; another process can claim the port before it is bound.

Both commands return status ``0`` when a check completes, including an ``unknown`` check or when no suggestions are found; status ``1`` indicates discovery failure; status ``2`` indicates invalid input or an unsupported JSON schema version. JSON errors use the version 1 ``error`` object and sanitized messages.

The JSON result has ``schemaVersion``, ``port``, ``namespace``, ``listeners``, ``messages``, and ``limitations`` fields. Each listener includes ``protocol``, ``state``, ``bindAddress``, ``addressFamily``, and ``owners``. Owner fields include ``pid``, ``processName``, ``command``, ``user``, and ``detailsStatus`` (``available``, ``permission-denied``, ``process-exited``, or ``unavailable``), plus ``projectContext`` with ``status``, evidence ``confidence`` (``high`` for owner cwd, ``medium`` for ancestor cwd, ``low`` when projects conflict, otherwise ``none``), ``source``, visible owner ``cwd``/``executable``, ``projectRoot``, ``gitDir``, ``gitCommonDir``, ``checkoutBranch``, ``checkoutCommit``, ``worktree``, bounded ``ancestors``, and evidence notes. The additive ``agentAttribution`` object includes ``status``, ``confidence``, opt-in ``agentName``/``sessionId``, source PID and relationship, ``leftoverAssessment``, UTC ``observedAt``, and evidence notes. Project context status is ``identified``, ``ambiguous``, ``not-found``, ``permission-denied``, ``process-exited``, or ``unavailable``. Sensitive command-line options, secret-like environment assignments, and URL passwords are redacted from process command details. When no process ID is visible, the listener's ``owners`` array is empty and the messages explain that permissions or namespace boundaries can hide ownership.

## ``portcn discover`` (`discover` / `snapshot`)

Linux-only. The ``discover`` command group includes ``snapshot``, which collects a unified discovery snapshot from native listeners, Docker, Podman, Nginx configuration, and systemd units through the shared coordinator. Output is additive: existing ``docker``, ``podman``, ``nginx``, and ``systemd`` command JSON is unchanged. Each relationship edge includes ``type``, ``confidence``, ``nature`` (`observed`, `configured`, `inferred`, `incomplete`, or `unavailable`), ``freshness``, evidence IDs, and scope. Docker context names come from `docker context show`. The snapshot resolves daemon host identity separately and reports missing endpoint evidence as unresolved. Use ``--full`` with ``--json`` to include provider observations. A systemd socket without a parsed network port retains unit-scoped configuration evidence and contributes no network endpoint relationship.

```sh
portcn discover snapshot
portcn discover snapshot --json
portcn discover snapshot --json --full
```

### ``discover project`` (Linux)

The nested ``project`` command is registered under ``discover``.

Resolves one Git checkout from the current directory or ``--project <path>`` and reports **native** runtimes for that checkout only. The default terminal view groups processes under inferred application scopes (``apps/<name>`` or ``packages/<name>`` from working directories), shows a short summary and visibility notes, and omits unrelated host listeners such as multicast SSDP/mDNS, Docker bridge UDP, and common system listeners. Mixed ownership and non-project owners on sockets that involve this checkout stay under ``Unresolved (project-relevant)``. Ownerless loopback listeners remain in ``listenerInventory.unknownOwnership`` and are not treated as confirmed project runtimes. Unknown ownership is distinct from positively classified unrelated host listeners. Portcn's own ``discover``/``mcp`` inspection processes are excluded when identifiable. Use ``--verbose`` for per-process evidence lines and the full unrelated listener inventory. ``--json`` remains additive: ``projectDiscovery.schemaVersion`` stays ``1`` while new fields such as ``summary``, ``applications``, ``excluded``, ``listenerInventory``, and ``visibilityNotes`` carry grouped and raw listener data without removing ``runtimes`` or ``limitations``. Container attribution, live TCP peer graphs, and MCP changes are out of scope ([#211](https://github.com/jayantrohila57/portcn/issues/211), [#212](https://github.com/jayantrohila57/portcn/issues/212)). ``discover snapshot`` and MCP contracts are unchanged.

```sh
portcn discover project
portcn discover project --project /work/acme
portcn discover project --verbose
portcn discover project --json
```

| Exit status | Meaning |
| --- | --- |
| ``0`` | Discovery completed, including partial visibility. |
| ``1`` | Discovery failed or the platform is unsupported. |
| ``2`` | Invalid project path or unsupported JSON schema version. |

With ``--json``, stdout emits ``{"schemaVersion":1,"projectDiscovery":{...}}`` with ``schemaVersion`` 1 inside ``projectDiscovery`` describing record shape.

## ``portcn mcp``

Starts a local read-only MCP server over stdio for coding-agent hosts. Configure the host to run ``portcn`` with the ``mcp`` argument. The server advertises ``list_listeners``, ``diagnose_port``, ``check_port_availability``, and ``suggest_ports``. On Linux it also advertises ``discovery_snapshot`` for bounded relationship summaries from the same coordinator as ``portcn discover snapshot``. Input schemas validate arguments before tool execution. Results are bounded and structured; tool errors use an error object with a stable code and a sanitized message. Stdout carries only MCP protocol messages, and SIGINT, SIGTERM, or client EOF closes the server.

The server reuses the CLI's Linux listener, process, project, and availability contracts. It does not execute arbitrary shell commands, inspect remote namespaces, start an HTTP endpoint, or change processes or ports. Diagnosis returns visible PID/process name and selected Git project fields, but omits process command lines, user identifiers, agent names, session IDs, and environment values. Port results are point-in-time snapshots, not reservations. See [MCP server for coding agents](/docs/guides/mcp) for tool bounds and client setup.

The result identifies the current network and PID namespace. It does not inspect the host or other namespaces, elevate privileges, change processes, or reserve a port. A no-listener result is a point-in-time observation, not a guarantee that a later bind will succeed. Compare protocol, address, and IPv4/IPv6 behavior with the server you plan to start.

| Exit status | Meaning |
| --- | --- |
| ``0`` | Diagnosis completed, including when no listeners are visible. |
| ``1`` | Discovery failed, the platform is unsupported, or ``ss`` is unavailable. |
| ``2`` | The port is not an integer from 1 through 65535, or the requested JSON schema version is unsupported. |

With legacy ``diagnose --json``, invalid arguments and discovery failures are emitted on stdout as ``{"error":{"code":"INVALID_PORT"|"DIAGNOSIS_FAILED","message":"...","port":"..."}}``. With ``--json-version 1`` (and on JSON-mode ``list``/``inspect`` errors), errors use ``{"schemaVersion":1,"error":{"code":"...","message":"...","port":"..."}}``; ``port`` is omitted for commands without a port argument. Terminal mode writes failures to stderr.

## Errors and limitations

- Linux requires ``ss`` from ``iproute2``; macOS listener discovery requires the system ``lsof`` command. The published macOS support is limited to ``list``, ``inspect``, and ``diagnose``. Windows listener discovery is unsupported.
- If ``ss`` is missing, install ``iproute2`` (Ubuntu: ``sudo apt install iproute2``). Portcn exits with status 1 instead of hiding the error.
- Failures or unexpected output from ``ss`` produce a nonzero exit and explanatory error. Hidden process metadata appears as `` - `` rather than an invented owner.
- Containers only see sockets in the current network namespace unless explicitly configured otherwise. ``diagnose`` shows the current namespace identifiers and does not inspect host namespaces automatically.
- ``list``, ``inspect``, and ``diagnose`` provide JSON output. Portcn does not kill processes or provide process/service management commands.

## Help and version

Running Portcn without arguments opens the dashboard in an interactive terminal and displays branded help when output is non-interactive. ``--help`` always displays help, while ``--version`` prints the package version. These paths return status 0.

```sh
node apps/cli/dist/index.js
node apps/cli/dist/index.js --help
node apps/cli/dist/index.js --version
```

Running `portcn` without a subcommand in an interactive terminal opens the listener dashboard. The dashboard uses the same tabbed, paginated view as `portcn list --interactive`; use `/` to search, `j`/`k` or arrow keys to select, `Enter` for process details, `s` to cycle sorting, and `:` for the command palette (`r` refreshes, `a` toggles five-second auto-refresh). Narrow terminals hide lower-priority columns rather than wrapping borders. In a non-interactive terminal, the command prints help instead.

See [Getting Started](/docs/getting-started) for local development.

For project discovery, a stable process whose own working directory resolves to the selected Git checkout retains its direct association when a parent launcher belongs to another checkout. Detailed evidence retains the ancestry conflict. Ancestor-only matches appear in `tentativeProcesses` and `listenerInventory.tentative`, outside the direct project counts.
