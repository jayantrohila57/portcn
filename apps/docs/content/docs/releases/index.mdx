This page is the single source of truth for releases. `AGENTS.md`, `CONTRIBUTING.md`, and workflow comments link here rather than maintaining separate procedures. Release Please is authoritative for versions, official changelog sections, tags, and GitHub Releases.

## Protected release flow

1. Merge validated task PRs into protected `dev`. Every release-relevant task has a generated `Unreleased` entry.
2. Prepare and review a `dev` → `main` promotion PR after the configured task threshold. Merge only with explicit authorization and required checks.
3. Release Please calculates SemVer from actual Conventional Commits, opens the release PR, and updates both package manifests, the manifest file, and `CHANGELOG.md`. Before `1.0.0`, `feat` and breaking changes advance the minor version; `fix` and `perf` advance the patch version. Docs and maintenance changes do not bump a release unless configured as release-relevant.
4. Merge the Release Please PR only after version, notes, package contents, and CI agree. Never edit versions or move an existing tag manually.
5. Verify the tag and release, publish npm and GitHub Packages independently, and record registry and installation results.
6. Open the authorized `main` → `dev` synchronization PR and merge it after checks pass. Clean only verified merged task branches.

Build dependencies in order with the frozen lockfile: `pnpm install --frozen-lockfile`, `pnpm --filter @portcn/core build`, then `pnpm --filter portcn build`. A release tag may be lightweight or annotated; checkout must resolve `v<version>^{commit}` to the release commit and must never move or recreate an existing tag.

## Package verification

The public npm package is the unscoped `portcn` package from `apps/cli`. The private workspace root and `@portcn/core` are never published. Before publication, run `npm pack --dry-run --json` and require `package.json`, `README.md`, `LICENSE`, the executable, source map, and bundled runtime dependencies. The consumer-facing [CLI README](https://github.com/jayantrohila57/portcn/blob/main/apps/cli/README.md) must describe only implemented behavior and is included in both release tarballs. Workflow validation rejects missing documentation or license files.

For npm Trusted Publishing, verify ownership and configuration before the release:

```sh
npm view portcn name repository --json
npm trust github portcn --repo jayantrohila57/portcn --file release-please.yml --allow-publish
npm trust list portcn
```

Publication uses OIDC provenance, checks for an existing exact version, and treats an exact existing version as an idempotent retry. A conflicting version or unknown registry response stops publication.

npm metadata can lag a successful publish because registries and local caches are eventually consistent. Use bounded retries with backoff (for example, five attempts with increasing delays), then verify all three surfaces:

```sh
npm view portcn@<version> version --prefer-online --registry=https://registry.npmjs.org/
curl --fail --silent https://registry.npmjs.org/portcn/<version>
tmp="$(mktemp -d)"; npm install --prefix "$tmp" --cache "$tmp/cache" -g portcn@<version>
"$tmp/bin/portcn" --version
"$tmp/bin/portcn" --help
```

If publication fails after the Release Please release exists, recover that release instead of creating another version or tag:

```sh
gh workflow run release-please.yml --ref main -f tag=v<version>
```

## GitHub Packages

The mirror package is scoped as `@jayantrohila57/portcn` and is published to `https://npm.pkg.github.com` with `GITHUB_TOKEN`, `contents: read`, and `packages: write`. The workflow stages the same CLI files, verifies the exact release commit, checks the tarball, skips an exact existing version, and publishes only the scoped package. Verify it independently with authenticated metadata and a clean install; set package visibility to public in repository Packages settings where supported.

The v0.1.0 GitHub Packages attempt remains unresolved: the workflow reached its release-tag guard and stopped before publication. Do not describe the mirror as successfully published until a later approved run records a successful workflow, package metadata, and installation. This does not invalidate the npm or GitHub Release artifact.
