This page is the single source of truth for releases. `CHANGELOG.md` is the canonical release history. The docs site renders its published sections directly at [`/whats-new`](https://github.com/jayantrohila57/portcn/tree/main/apps/docs/app/whats-new); do not maintain a second release list.

## Protected release flow

1. Merge each validated task PR into protected `dev`. A single completed feature or fix can qualify for a release; do not wait for a task-count threshold. The promotion preview requires a real SemVer bump from a change to shipped source under `apps/cli/` or `packages/core/`. Documentation, workflows, and release tooling do not qualify on their own.
   Documentation-only task PRs can update contributor and release guidance without adding an `Unreleased` entry. Keep the changelog focused on shipped changes; the task and CI validators accept an unchanged changelog only when every changed path is documentation.
   Staged Biome checks cover supported Markdown files and exclude Fumadocs MDX; `pnpm docs:check` and the docs build validate MDX content and links.
2. Prepare a `dev` → `main` promotion PR after a meaningful release candidate is ready. Preserve task commits. Run the workspace checks and review the changelog candidate. Merge only after the repository owner explicitly approves.
3. Release Please runs on `main`, calculates SemVer from Conventional Commits, and opens a release PR. It remains authoritative for the version manifest, root and CLI package versions, release PR, Git tag, and GitHub Release. Before `1.0.0`, features and breaking changes advance the minor version; fixes and performance changes advance patch; from `1.0.0`, breaking changes advance major.
4. Write user-facing notes into `CHANGELOG.md` using Keep a Changelog headings: `Unreleased`, then `Added`, `Changed`, `Fixed`, `Deprecated`, `Removed`, and `Security`. Version headings use `## [X.Y.Z] - YYYY-MM-DD`; dates are IST. Include an issue reference where one exists and a version comparison link. Use `node scripts/task-lifecycle.mjs changelog "feat(cli): describe the change" <issue-number>` to add a concise pending entry.
5. Before approving the Release Please PR, run `node scripts/generate-release-notes.mjs <new-version> <previous-version> "<meaningful release title>"` from its candidate branch. Review and commit the dated canonical section there so protected checks validate the final candidate. Review the exact version, package files, comparison link, changelog, and CI together. Do not edit versions manually or create/move/delete tags. Existing release history is immutable; correct mistakes by fixing forward.
6. After the approved Release Please PR merges, verify the GitHub Release and that `v<version>^{commit}` resolves to its exact release commit. Publish npm and GitHub Packages independently using the approved, exact-tag workflows. Each skips an exact version that already exists and stops on a conflicting version or an unknown registry result.
7. Recover a failed publication against the existing tag; do not create another version or tag. For npm, use the release workflow’s `workflow_dispatch` exact-tag recovery. GitHub Packages can be dispatched using `gh workflow run github-packages.yml --ref main -f tag=v<version>`. Verify each registry independently.
8. Open the documented `main` → `dev` synchronization PR and merge after its required checks pass.

## SemVer and release notes

Conventional Commit types drive automatic version calculation: `feat` is minor before 1.0.0 and minor afterward; `fix`/`perf` are patch; `!` or `BREAKING CHANGE:` selects the breaking bump (minor before 1.0.0, major from 1.0.0). Docs, tests, build, CI, refactor, and maintenance-only commits do not bump the CLI release unless the change is explicitly classified as user-facing.

`CHANGELOG.md` is the only hand-authored release history. `scripts/generate-release-notes.mjs <version> <previous-version> "<meaningful release title>"` generates a release section from Conventional Commits and their PR/issue references. The generator uses the IST calendar date, requires an editorial title, rejects duplicate release versions, and resets `Unreleased` only after creating the versioned entry. Release Please is configured not to generate a parallel changelog section. Its `GITHUB_TOKEN` cannot push a follow-up changelog commit and retrigger the protected PR checks, so the candidate branch update must be made and committed by an authorized reviewer before approval.

For historical audits, verify every release boundary against tags, GitHub Releases, merged PRs, issues, and source snapshots. Record discrepancies and prepare exact Release description drafts; obtain explicit approval before changing an already-published GitHub Release. See [`RELEASE-HISTORY-AUDIT.md`](https://github.com/jayantrohila57/portcn/blob/main/RELEASE-HISTORY-AUDIT.md) for the current audit and review drafts.

Historical v0.0.1, v0.1.0, and v0.1.1 notes have been retained from their existing published GitHub Release/tag records. Do not rewrite those artifacts. The current release notes may be editorially improved only when their shipped behavior and references remain accurate.

## Package verification and publication recovery

The public npm package is the unscoped `portcn` package from `apps/cli`. The private workspace root and `@portcn/core` are never published. Before publication, run `npm pack --dry-run --json` and require the executable, source map, bundled runtime dependencies, README, and license.

For npm Trusted Publishing, verify ownership and configuration before the release:

```sh
npm view portcn name repository --json
npm trust github portcn --repo jayantrohila57/portcn --file release-please.yml --allow-publish
npm trust list portcn
```

Publication uses OIDC provenance, checks for an existing exact version, and treats that exact version as an idempotent retry. Conflicting metadata or an unknown registry response stops publication.

Verify each registry and a fresh install independently:

```sh
npm view portcn@<version> version --prefer-online --registry=https://registry.npmjs.org/
curl --fail --silent https://registry.npmjs.org/portcn/<version>
tmp="$(mktemp -d)"; npm install --prefix "$tmp" --cache "$tmp/cache" -g "portcn@<version>"
"$tmp/bin/portcn" --version
"$tmp/bin/portcn" --help
```

GitHub Packages is `@jayantrohila57/portcn` on `https://npm.pkg.github.com`. Its workflow verifies the exact tag commit, stages the same CLI files, skips an exact existing version, and publishes only the scoped package. Verify it with authenticated metadata and a clean install; configure public package visibility in repository settings where supported.

The v0.1.0 GitHub Packages attempt remains unresolved: the workflow reached its release-tag guard and stopped before publication. Do not describe the mirror as published until an approved run records successful workflow, package metadata, and installation. The npm and GitHub Release artifacts are separate.
