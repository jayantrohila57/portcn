The repository's [CONTRIBUTING.md](https://github.com/jayantrohila57/portcn/blob/main/CONTRIBUTING.md) is the canonical contributor policy. This page summarizes the development path and links to it rather than maintaining a competing copy.

## Task workflow

### Read instructions and inspect the checkout [step]

Read the root and nearest scoped `AGENTS.md`, check the working tree, fetch `origin/dev`, and preserve existing work.

### Create a task branch [step]

Use the existing checkout for one task at a time. From a clean `dev`, run `node scripts/task-lifecycle.mjs start feat/example` to fetch and create a task branch. Task PRs target `dev`. Contributions may come from forks: use an approved task branch name, keep the PR title and commits Conventional, and do not request write access or secrets. Fork PRs receive the same read-only validation and changelog checks; only trusted repository branches can promote or release.

### Identify documentation impact before coding [step]

For changes to behavior, commands, packages, dependencies, architecture, security, configuration, tooling, or contributor workflows, identify affected documentation first. Update the Fumadocs pages in the same task and verify examples against implementation. If no docs apply, explain why in the PR.

### Run checks and open a PR [step]

Use the repository scripts and include a documentation summary naming changed pages or a justified `No documentation change required`. Use a Conventional Commit title. Run `node scripts/task-lifecycle.mjs submit "feat(cli): describe the change" /path/to/pr-body.md` after committing and checking your changes. It creates or reuses the PR and requests auto-merge. CI requires an updated Fumadocs page or `No documentation change required:` followed by a specific explanation. Routine task pushes and merges into `dev` are authorized after required checks pass. Once merged, run `node scripts/task-lifecycle.mjs finish` from the clean task branch. Preserve the branch if checks or merge are blocked.

## Release notes

`CHANGELOG.md` is the canonical Keep a Changelog history; `/whats-new` renders its published sections directly. A single meaningful feature or fix can qualify for release promotion. Add a concise categorized `Unreleased` entry with `node scripts/task-lifecycle.mjs changelog "feat(cli): describe the change" <issue-number>` when the change has an issue. Use IST dates and the release runbook's six categories. Before approving a Release Please PR, generate and commit the dated release notes on its candidate branch so CI validates the final changelog. Release Please remains the version and tag authority, and production release approval remains explicit.

When resuming an existing task PR, use its exact Conventional title for submission and the changelog entry. A title mismatch stops submission for reconciliation.
