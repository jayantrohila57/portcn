The [SECURITY.md policy](https://github.com/jayantrohila57/portcn/blob/main/SECURITY.md) is the canonical vulnerability reporting process. Do not report vulnerabilities in public issues; use GitHub's private vulnerability reporting when available.

## Current execution behavior

The Linux CLI reads listening sockets from the current network namespace through `ss` and may read visible process metadata from `/proc`. The `diagnose` command uses an owner process's working directory and up to five ancestors to query Git for project/worktree metadata. With opt-in `PORTCN_AGENT_SESSION_ID` and optional `PORTCN_AGENT_NAME` markers, it inspects owner and ancestor environment files to extract only those exact keys; it does not retain or emit other environment values, agent conversations, or prompt data. `assess <pid>` compares visible project/session evidence and checks PID start time before and after collection; it remains limited to the current PID namespace and permissions. `verify <endpoint>` reads TCP listener and current checkout metadata only; it does not connect, issue HTTP requests, check TLS, or prove which code a process loaded. These reads are bounded, read-only, and may be incomplete due to permissions, process exits, namespaces, or missing Git metadata. The output includes visible filesystem paths and executable locations. Agent markers are user-supplied evidence, not authenticated identities; possible leftover status is not evidence that a process is safe to stop. Portcn does not elevate privileges, change sockets, or terminate processes. Host `ss` queries use only the current network namespace and do not inspect other namespaces automatically. The development `docker` command invokes read-only Docker CLI list and inspect operations through the selected daemon context, which may be remote. It requires the user's existing Docker CLI and daemon permissions, does not start or stop containers, and does not expose a Docker socket to another process. The `exposure` command combines local listeners with Docker metadata; it does not inspect firewalls, routes, or internet reachability, and the two sources may describe different hosts. The Docker test workflow mounts Git metadata read-only and does not expose the Docker socket.

The ``config`` commands store user-authored service identities, favorites, aliases, notes, and group names in the user's XDG config directory; development builds also support an optional local HTTP(S) URL override. The directory is restricted to owner access and the JSON file to mode ``0600``. Listener status is recomputed at read time; process metadata and discovery results are not saved. A validated previous config is retained as a local backup for recovery. ``endpoint check`` sends one bounded HTTP HEAD request only after the user selects a saved service; it does not follow redirects and retains default TLS certificate validation. ``open`` requires an explicit service ID and starts ``xdg-open`` directly with the validated local URL as one argument, without a shell.

``readiness check`` is also opt-in and targets only a currently observed local TCP service. Without a saved URL it performs bounded TCP connection attempts and reports reachability, not application health. A saved URL is validated as local HTTP(S) and matching the service port; readiness sends bounded HTTP HEAD requests, does not follow redirects, and keeps default TLS checks. Timeouts, retries, and intervals have hard limits; Ctrl-C and SIGTERM cancel the work. A listener snapshot alone is never reported as ready. The command does not run arbitrary shell checks, contact external hosts, restart services, or change system state.

``connection check`` diagnoses one selected local service from the CLI process's current network namespace. Resolution remains limited to the service's local name or address; TCP connects use a bounded timeout, and an HTTP request is sent only when an explicit, validated local URL is saved. Redirects are not followed and TLS certificate checks stay enabled. Docker data comes from the selected Docker CLI context and reports port mapping configuration only; it is not a test from inside a container or proof of reachability, especially for remote contexts. The command does not scan external hosts, inspect firewall rules, execute commands in containers, or change system state.
