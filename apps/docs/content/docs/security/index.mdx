## Current execution behavior

The Linux CLI reads listening sockets from the current network namespace through `ss` and may read visible process metadata from `/proc`. The published macOS adapter for `list`, `inspect`, and `diagnose` uses `lsof` without elevation; it reports visible PIDs/process names but does not read command lines, user IDs, project paths, or agent environment markers. On Linux, `diagnose` uses an owner's working directory and up to five ancestors to query Git project/worktree metadata. With opt-in `PORTCN_AGENT_SESSION_ID` and optional `PORTCN_AGENT_NAME` markers, it reads only those exact keys from visible process environment files; it does not retain or emit other environment values, agent conversations, or prompt data. `assess <pid>` compares visible project/session evidence and checks PID start time before and after collection; it remains Linux `/proc`- and permission-dependent. `verify <endpoint>` reads TCP listener and current checkout metadata only; it does not connect, issue HTTP requests, check TLS, or prove which code a process loaded. These reads are bounded, read-only, and may be incomplete due to permissions, process exits, namespaces, or missing Git metadata. The output includes visible filesystem paths and executable locations when available. Agent markers are user-supplied evidence, not authenticated identities; possible leftover status is not evidence that a process is safe to stop. Portcn does not elevate privileges, change sockets, or terminate processes. Host `ss` queries use only the current network namespace and do not inspect other namespaces automatically. Podman `rootlessport` attribution reads only visible `/proc/<pid>/stat`, `cmdline`, and `exe` data for listener owners. It checks PID start time before and after inspection and again before attribution, requires structured mapping arguments to match the published host binding and container network address, and emits no raw command line. Missing permissions, changing process identity, incomplete arguments, and conflicting candidates remain unknown or ambiguous; Portcn does not elevate privileges. The `docker` command uses read-only list and inspect operations through the selected Docker context. The `podman` command uses read-only list and inspect operations through the invoking user's configured Podman connection, which may be rootless, rootful, or remote. Neither command starts, stops, execs into, or reconfigures containers, elevates privileges, or exposes a runtime socket to another process. Host listener comparisons are current-namespace observations and may describe a different host from a remote runtime. The `exposure` command combines local listeners with Docker metadata; it does not inspect firewalls, routes, or internet reachability. The Docker test workflow mounts Git metadata read-only and does not expose a Docker or Podman socket.

The ``config`` commands store user-authored service identities, favorites, aliases, notes, and group names in the user's XDG config directory; saved services can include an optional local HTTP(S) URL override. The directory is restricted to owner access and the JSON file to mode ``0600``. Listener status is recomputed at read time; process metadata and discovery results are not saved. A validated previous config is retained as a local backup for recovery. ``endpoint check`` sends one bounded HTTP HEAD request only after the user selects a saved service; it does not follow redirects and retains default TLS certificate validation. ``open`` requires an explicit service ID and starts ``xdg-open`` directly with the validated local URL as one argument, without a shell.

``readiness check`` is also opt-in and targets only a currently observed local TCP service. Without a saved URL it performs bounded TCP connection attempts and reports reachability, not application health. A saved URL is validated as local HTTP(S) and matching the service port; readiness sends bounded HTTP HEAD requests, does not follow redirects, and keeps default TLS checks. Timeouts, retries, and intervals have hard limits; Ctrl-C and SIGTERM cancel the work. A listener snapshot alone is never reported as ready. The command does not run arbitrary shell checks, contact external hosts, restart services, or change system state.

``connection check`` diagnoses one selected local service from the CLI process's current network namespace. Resolution remains limited to the service's local name or address; TCP connects use a bounded timeout, and an HTTP request is sent only when an explicit, validated local URL is saved. Redirects are not followed and TLS certificate checks stay enabled. Docker data comes from the selected Docker CLI context and reports port mapping configuration only; it is not a test from inside a container or proof of reachability, especially for remote contexts. The command does not scan external hosts, inspect firewall rules, execute commands in containers, or change system state.

The ``mcp`` command uses stdio only and exposes bounded read-only listener, owner/project, and port-availability queries. It does not expose a shell, process-control operation, HTTP listener, or agent inference. Tool responses omit process command lines, user identifiers, agent names, session IDs, and environment values. MCP stdout contains protocol data only; SDK diagnostics, if any, go to stderr.
