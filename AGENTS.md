# Repository guidance

- Read the nearest `AGENTS.md` before changing a directory; keep `apps/docs` independently installable/buildable as a workspace app.
- Executable applications belong in `apps/`; reusable, platform-independent libraries belong in `packages/`.
- Put shared domain rules in `@portcn/core`; keep CLI presentation and future Linux-specific integrations outside the core package.
- Keep the root package private and named `@portcn/workspace`. Reserve the unscoped npm package name `portcn` for `apps/cli`.
- Use existing pnpm, Turborepo, Biome, TypeScript, and Vitest configuration. Avoid duplicate tools and dependencies.
- Install dependencies with the frozen lockfile; Husky runs staged Biome and Commitlint checks, then the full workspace validation suite before each commit. CI runs its checks directly with hooks disabled.
- Run Git hooks and workspace checks with the regular pnpm scripts; CI runs checks directly on GitHub Actions with hooks disabled. Docker Compose remains available for optional packaged CLI image checks (`pnpm docker:cli`, `pnpm docker:build`, `pnpm docker:clean`).
- Container CLI runs initially observe only their own PID, network, and mount namespaces. Do not add privileged mode, host PID/network namespaces, or Docker socket mounts by default.
- Preserve strict TypeScript, focused tests, the existing docs branding/theme, and clear errors. Do not claim functionality that is not implemented.
- Update release metadata consistently for the CLI package, workspace root, and Release Please manifest; never edit versions outside Release Please.
- Use Conventional Commits for every commit and PR title; do not add compatibility exceptions for narrative subjects. Use Conventional squash titles for task PRs and `chore(main): ...` for promotions and synchronizations.
- Routine task pushes, PR creation and merging into dev are authorized when required checks pass. Never merge to main, publish, tag, or deploy without explicit authorization. Preserve existing tags.
- Run the relevant lint, format, type, test, build, release, and package checks before proposing changes.
- Use only this existing repository directory: no additional worktrees, clones, or parallel coding tasks. Check the working tree and existing branches/PRs, preserve uncommitted work, read applicable guidance, fetch `origin/dev`, and create one task branch from updated `dev`. Never edit directly on `main` or `dev`. `node scripts/task-lifecycle.mjs start <type/name>` performs the clean start checks.
- Use `feat/*`, `fix/*`, `refactor/*`, `chore/*`, `docs/*`, `test/*`, `build/*`, `ci/*`, or `perf/*` task branches. Open PRs to `dev` and integrate automatically after required checks pass. Use `node scripts/task-lifecycle.mjs submit <title> <body-file>` to push, create or reuse the PR, and request GitHub auto-merge; never bypass protections. Preserve the branch and report blockers. After merge use `node scripts/task-lifecycle.mjs finish` to verify the merged PR and return to updated `dev`.
- A single completed, release-relevant feature or fix can qualify for a release; do not wait for a task-count threshold. Prepare a promotion PR only when the SemVer preview contains a real release candidate. Keep task commits during promotion; Release Please runs only on `main` and remains authoritative for package versions, manifest, tags, and GitHub Releases. Never merge a production release PR, create a release tag, or publish packages without explicit authorization.
- Release eligibility must reflect shipped behavior: only Conventional feature/fix/performance/breaking changes touching `apps/cli/` or `packages/core/` qualify. Workflow, scripts, docs, tests, and release-tooling changes alone must not create a product version bump even if the task PR title starts with `feat`.
- After release, synchronize `main` back to `dev` through the explicitly allowed sync PR. Never rewrite published history or move/delete tags.
- Report current branch, task status, checks run, PR target, and remaining steps at completion.
- Branch policy runs only for PR events. Full validation also runs on pushes to both `dev` and `main`.
- Documentation is a required deliverable in the same task and PR for every change that affects users, contributors, architecture, dependencies, configuration, workflows, security, or development. Before coding, identify affected docs; update them alongside implementation and verify examples against code. If none apply, explain why in the PR. Never mark work complete while required docs are missing or inaccurate.
- Every PR description must summarize documentation changes by page, or justify `No documentation change required`. CI checks MDX builds, practical internal links, and objective CLI reference consistency; reviewers assess semantic completeness and accuracy.
- When authoring Fumadocs MDX, use the centrally registered components documented in `apps/docs/content/docs/development/mdx-components.mdx` where they improve the content: Steps for sequential procedures, Tabs for equivalent alternatives, Callouts for important context, Cards for navigation, Accordions for optional troubleshooting, Files for real repository structure, TypeTable for real types/options, and highlighted fenced code for verified commands.

- Before committing a user-facing task, generate and review its categorized `Unreleased` entry with `node scripts/task-lifecycle.mjs changelog "<Conventional PR title>" [issue-number]`. Documentation-only PRs leave `CHANGELOG.md` unchanged when every changed path is documentation; local and CI validators enforce that scope. `CHANGELOG.md` is the canonical Keep a Changelog source; dated release headings use IST and the docs render published entries at `/whats-new`. Follow `apps/docs/content/docs/releases/index.mdx`; Release Please remains the sole version/tag authority and must not generate a competing changelog history.
- Before approving a Release Please candidate, run `node scripts/generate-release-notes.mjs <new-version> <previous-version> "<meaningful release title>"` in its candidate branch, review and commit the canonical dated section so required CI checks run on the final versioned notes. The workflow uses `GITHUB_TOKEN`, which does not trigger follow-up PR workflows for its commits.
- For historical changelog or GitHub Release edits, verify each claim against its tag boundary, published release, merged PR, linked issue, and source snapshot. Draft changes first and obtain explicit approval before editing a published GitHub Release description. See `RELEASE-HISTORY-AUDIT.md` for the verified history and process.
